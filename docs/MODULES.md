# Модульная система

## Реализованный локальный runtime

Локальные доверенные C++-модули теперь устанавливаются из `.qmod` и выполняются
отдельными процессами, по одному на узел Workspace. Это не sandbox.
Создание, сборка, установка, UI, события и порты описаны в
[LOCAL_MODULES.md](LOCAL_MODULES.md). Онлайн-каталог остаётся metadata-only.

## Целевая модель поставки

Ядро движка поставляется без каталога модулей и без встроенных feature-модулей.
После установки приложение получает каталог из Supabase и устанавливает выбранные
пакеты отдельно. Это уменьшает размер базовой поставки и позволяет обновлять
модули независимо от движка.

У модуля есть два независимых измерения:

1. **Происхождение** — `system` или `user`.
2. **Состояние публикации** — draft, submitted, published, rejected или suspended.

Системные модули публикуются только доверенным сервисом NerveGears. Пользователь
может создавать только собственные `user`-модули; публикация проходит проверку
манифеста, пакета и подписи.

### Граница выполнения

Модуль не получает Flutter-контекст или host-команды изменения shell.
Локальный `native-process-v1` изолирует память и аварии процесса, но не доступ
к файловой системе, сети или устройствам. Прежняя идея подписанного WASM sandbox
не реализована и не является текущим контрактом локальных C++-модулей.

Host API модуля ограничен:

- входной и выходной `SampleBlock` текущего pipeline;
- декларативные параметры модуля;
- события и метрики через явно выданные capabilities;
- логирование с ограничением частоты.

UI модуля описывается декларативным manifest/UI schema. Для локальных `.qmod`
поддерживается host-rendered `uiLayout` с карточками, строками/колонками,
кнопками, значениями и графиками истории. Модуль может рендерить
только содержимое активного рабочего окна и правого inspector. Host может показать ту же
активную область на весь экран или в отдельном нативном окне;
модуль не получает самостоятельного доступа к управлению этими окнами.
Он не может менять shell, Explorer, rail, top bar, настройки, auth или другие
разделы. Любые действия модуля проходят через allowlist команд host API.

### Жизненный цикл

```text
catalog -> download manifest -> verify signature/hash -> install locally
        -> permission review -> load sandbox -> enable in workspace
        -> update (new immutable release) -> disable/uninstall
```

Для каждого установленного модуля локально хранятся `module_id`, выбранная
версия, hash пакета, разрешённые capabilities и состояние enable/disable.
Нельзя заменять опубликованный release на месте: обновление создаёт новую
неизменяемую версию.

## Supabase-модель

Миграции в `supabase/migrations/` создают:

- `profiles` — публичные данные пользователя, связанные с `auth.users`;
- `modules` — каталог и владельца модуля;
- `module_releases` — неизменяемые версии, manifest, hash и подпись;
- `module_installations` — установленная версия и выданные capabilities на
  пользователя;
- private Storage bucket `module-packages` для архивов.

Credentials и OAuth identities не дублируются в public tables: ими управляет
Supabase Auth. Google, GitHub и email/password включаются в Authentication /
Providers, а клиент получает только session/access token. Пакеты выдаются через
Edge Function короткоживущими signed URLs после проверки опубликованного
release.

Ключевые RLS-правила:

- anonymous/authenticated видят только опубликованный каталог;
- пользователь создаёт и изменяет только собственные draft user-модули;
- system-модули и публикация releases доступны только trusted service role;
- опубликованные package metadata и bytes не редактируются.

## Текущий legacy-контракт C++

Этот контракт сохраняется только для встроенного прототипа pipeline. Перед
переходом на удалённые модули он будет вынесен в доверенный system-module host.

```cpp
class IModule {
 public:
  virtual ~IModule() = default;
  virtual const ModuleInfo& info() const = 0;   // id, имя, категория, версия
  virtual void init(EngineContext& ctx) {}      // один раз при старте движка
  virtual void process(SampleBlock& block) = 0; // блок сэмплов (интерлив)
};
```

`SampleBlock` — интерливнутый буфер `[frame * channels + channel]`,
плюс sample_rate и глобальный индекс первого сэмпла.

## Пользовательские модули (v0.2+)

Старые встроенные демонстрационные записи каталога удалены. Пользовательские черновики
создаются в Supabase Auth-контексте и связаны с `auth.uid()` автора. В текущей
версии они отображаются в рабочем пространстве. Для локальных доверенных
пакетов реализованы installation store и native-process-v1. Нативные
динамические библиотеки из интернета не загружаются в процесс движка;
автоматическое исполнение remote-пакетов не реализовано.

## Marketplace и Workspace

`Marketplace` получает только опубликованные metadata из `modules` и последнего
опубликованного `module_releases`. Бесшовная подгрузка выполняется страницами по
24 записи; карточка может показывать `cover`, автора, статистику, даты и
категории из metadata. Действие **Add to Workspace** сохраняет manifest в
локальной библиотеке, но не является установкой бинарного пакета и не запускает
удалённый код. Встроенные Qualia Dark и Qualia Light представлены как локальные
темы каталога.

Для тестирования интерфейса добавлен отдельный локальный playground:
24 module placeholders и 12 extension placeholders из
`app/lib/core/modules/module_preview_data.dart`. Названия помечены `Preview`,
slugs используют namespace `qualia.preview.*`, manifest содержит `preview: true`.
Они не публикуются в Supabase и не исполняют код. В Explorer Workspace доступны
первые восемь типов модулей: их можно перетаскивать на канвас, соединять порты,
менять параметры экземпляра и открывать декларативный UI. Остальные варианты
предназначены для проверки прокрутки карточек.

Фильтры Category/Appearance, License, Published и Availability разделены на
общие panel-блоки с независимой от каталога прокруткой. Лицензия читается из
строкового `manifest.license` (например, SPDX ID `MIT`, `Apache-2.0` или
`GPL-3.0-only`); произвольные названия тоже поддерживаются. Отсутствующее поле
означает `Unspecified`, а не открытую лицензию. Значения лицензий preview-записей
— исключительно примеры для тестирования фильтров, не лицензии реальных пакетов.

В широком окне ширину панели фильтров можно менять перетаскиванием её правой
границы (200–420 px, с ограничением по ширине окна). Выбор сохраняется локально;
в узком окне используется прежний компактный диалог фильтров.

Тексты Marketplace используют размер 14. Grid использует ленивую masonry-сетку:
карточки разной высоты заполняют самую короткую колонку без выравнивания рядов.
Обложка всегда имеет пропорции 16:9 независимо от метаданных автора;
меняется только высота нижней части с описанием и информацией о модуле.
Сетка сохраняет подгрузку страниц,
фильтрацию и сортировку; в узком окне остаётся одна колонка.
List сохраняет прежнюю раскладку и переключается на вертикальную карточку в узком окне.
Лицензии в фильтрах выбираются через `DesktopSelectField` с выпадающим списком,
в том числе в компактном диалоге; выбранные значения сохраняют стабильные IDs.
Заголовок License использует общий `_filterBlock`: жирность, размер и отступы
совпадают с Category, Published и Availability; подпись внутри поля не дублируется.
Между опциями фильтров — 6 px, общие скроллбары — 3 px. Rail Settings
занимает 60% ширины окна (минимум 600 px, но не выходит за доступную область).

`Workspace` хранит граф экземпляров модулей отдельно от каталога. Узлы можно
перемещать, связывать через входы/выходы, масштабировать и панорамировать;
самоссылки, отсутствующие порты и циклические processing-связи отклоняются.
ПКМ по узлу открывает `Open`, `Replace module`, цвет заголовка, выбор узлов того
же цвета и `Delete`; ПКМ по свободной области открывает встроенный поиск модулей
над `Add`. При непустом запросе Add заменяется выдачей поиска; если совпадений
нет, показывается локализованное сообщение. Кнопка `Open` показывает декларативную активную область модуля, а
inspector использует allowlist-контролы `slider`, `toggle`, `select`, `text`,
`number`, `button` и `label`.

### Клавиатура, Inspector и окна модулей

Общие desktop-кнопки, пункты рейла, Explorer, настройки, карточки и вкладки
поддерживают **Tab / Shift+Tab**, видимую рамку фокуса и активацию
**Enter / Space**. Отключённые действия пропускаются. Меню используют
**↑ / ↓** для перехода, **→** для подменю, **← / Esc** для возврата/закрытия;
после закрытия фокус возвращается к кнопке. Текстовые поля и стандартные
Flutter-контролы сохраняют обычное редактирование с клавиатуры.
**Shift+F10** или клавиша контекстного меню открывает действия узла/порта.
Для соединения портов можно перейти к каждому через Tab и активировать Enter.
В Settings добавлен раздел **Navigation / Навигация** с общей справкой по
Tab/Shift+Tab, активации, меню, контекстным действиям и полноэкранным модулям.
Отдельная вкладка Keyboard shortcuts удалена: сочетания редактируются в Navigation
и в той же панели из global search. `navigation_bindings.dart` хранит реальные
команды, сохраняет переназначения в preferences и используется кнопками, меню,
канвасом и окнами модулей. Редактор захватывает клавишу с модификаторами, проверяет
конфликты, поддерживает Save / Ctrl+Enter, отмену Esc и сброс всех сочетаний.
Рамка фокуса видна только при клавиатурной навигации; мышь/тачпад скрывают её,
не сбрасывая выделение графа. Обычный ввод и движение курсора в тексте её не включают.

Правый Inspector имеет фиксированную шапку и прокручиваемые блоки на общей
поверхности `DesktopPane`: экземпляр, параметры, оформление, входы/выходы,
соединения. Блоки используют переиспользованный `ExplorerDisclosureSection`
и сворачиваются мышью или с клавиатуры. Из Inspector доступны Open,
отдельное окно и полноэкранная область.

В активной области модуля кнопка Fullscreen или **F11** открывает ту же UI
schema без shell, рейла и Explorer, на root navigator. При доступности
`window_manager` включается нативный fullscreen; **Esc**, Back или F11
возвращают прежнюю область и состояние окна, не сбрасывая параметры.
Отдельное окно доступно из активной области, Inspector, кнопки в узле канваса
и контекстного меню узла.

Отдельное окно — процесс того же executable с режимом `--module-window`.
Он не запускает auth или второй Workspace и не пишет общие preferences.
Основной процесс остаётся владельцем параметров экземпляра. Host-owned
WebSocket на IPv4 loopback с одноразовым случайным token передаёт snapshot
и обновления; клиент может менять только параметры allowlist-контролов с
проверкой типов. Закрытие окна не удаляет узел. Повторное открытие того же
экземпляра фокусирует существующее окно. Удаление узла, завершение host или
разрыв соединения закрывает дочернюю область; новая копия processing-графа
не запускается. Язык и тема берутся из основного окна при открытии.
UI реализован общей `ActiveModuleView` для всех трёх режимов; установленный
локальный C++-экземпляр остаётся один и тот же во всех этих представлениях.

Строка вкладок в Workspace удалена. Вместо неё используются меню **Add**
(модуль / Marketplace), **Select** (всё / снять выделение / удалить выделенное)
и **View** (масштаб, вписать граф/выделение, inspector). Все host-owned меню
переиспользуют `DesktopMenuSurface` из `features/common/desktop_menu.dart`:
тот же фон, скругления, тень и hover, что и меню топбара. Для Add / Select / View
используются увеличенные строки 48 px и ширина 320 / 340 / 360 px с ограничением
viewport; стандартные меню сохраняют строки 38 px. Кнопка правой панели
закреплена справа в этой же строке инструментов.
Вертикальный padding кнопок Add / Select / View уменьшен до 9 px.
Значения действий и авторских select-параметров не зависят от языка интерфейса.
Узел может иметь одну из host-owned цветовых групп: без цвета, красный,
оранжевый, жёлтый, зелёный, синий или фиолетовый. Цвет сохраняется вместе с
графом, окрашивает header, доступен в inspector и применяется к выделению
группой. В меню `View` цветом можно фильтровать видимые узлы; фильтр не удаляет
скрытые узлы и связи из графа.
Каждый вход/выход имеет независимый host-owned цвет подсветки (`inputColors` /
`outputColors`), который выбирается ПКМ по строке порта или в inspector.
Цвета не записываются в авторские параметры. Старые графы и неизвестные цвета
восстанавливаются без подсветки. Вся половина строки (высота 32 px) принимает
клик и drag-соединение, а не только видимая точка или текст.
Линия наследует цвета output и input: разные цвета дают плавный градиент от
источника к приёмнику, одинаковые — однотонную связь. Неокрашенный конец остаётся
нейтральным, а связь без подсветки с обеих сторон — серой. Предпросмотр при
перетаскивании также использует цвет выбранного порта.
ПКМ по порту открывает **Название → Значение → Цвет**. Цвет и тип значения
выбираются в подменю, которое открывается наведением или клавишей →.
Название редактируется в общем диалоге; пустое поле восстанавливает исходное имя.
Отображаемые названия (`inputLabels` / `outputLabels`) сохраняются отдельно от
стабильных manifest IDs, поэтому переименование не меняет существующие связи.
Типы значений (`inputTypes` / `outputTypes`) — host-owned аннотации: любое,
строка, число, логическое, список или объект. Они сохраняются в графе, но пока
не выполняют конвертацию данных или runtime-проверку processing-потока.
Порты и кнопки добавления Input/Output имеют прямоугольную форму со скруглениями.
Категория и версия не занимают отдельную строку в узле канваса; metadata остаются
в карточках и активной области модуля.

Масштаб графа: 25–200%, Ctrl+прокрутка / pinch-жест, кнопки −/+ снизу и меню View.
Ctrl+Plus/Minus меняют масштаб, Ctrl+0 возвращает 100%, F вписывает граф,
эти клавиатурные команды работают при наведении на канвас без первого клика.
Ctrl+A выделяет всё, Shift+клик добавляет узел в выделение, Delete удаляет
выделенные узлы и их связи. Узлы перемещаются за заголовок; множественное
выделение перемещается группой. Правый нижний угол изменяет ширину и высоту
узла независимо от масштаба канваса. Размеры сохраняются вместе с графом;
старые сохранения без размеров совместимы. Минимальная высота вычисляется по
числу портов, поэтому добавление inputs/outputs не обрезает содержимое.
Перемещение выделенной группы публикует одно изменение графа на pointer-событие,
а не отдельное изменение для каждого узла. Узлы и фон канваса отделены
repaint-boundaries; точки рисуются пакетно, связи используют индекс узлов по ID.
Сетка состоит из вложенных слоёв 96 / 48 / 24 logical px. Опорные точки
сохраняют яркость; промежуточные плавно меняют прозрачность по smoothstep
на диапазонах масштаба 35–65% и 75–125%, без скачка плотности в 50% / 100%.
Прозрачность догоняет zoom за 120 ms и при крупных шагах; позиции точек следуют
трансформации сразу, без задержки канваса. Reduced-motion отключает анимацию.

ЛКМ с перетаскиванием по пустому канвасу выделяет узлы рамкой (пересечение
с областью); Shift добавляет область к выделению. Space + ЛКМ, Alt + ЛКМ
или средняя кнопка мыши панорамируют канвас, не изменяя позиции узлов.
Колёсико нужно удерживать при движении мыши; Space для этого не требуется.
Прокрутка двумя пальцами на тачпаде перемещает доску по обеим осям; обычное
колесо также прокручивает доску. Поддерживаются как Linux scroll-события,
так и нативные pan/zoom-жесты тачпада. Pinch меняет масштаб вокруг точки жеста.
Drag & Drop модуля из Explorer не перекрывает канвас панелью или размытием;
drop добавляет экземпляр в позицию указателя. `user&dev switcher` удалён с рейла;
разделы остаются доступны через его настройки.

Фон канваса — адаптивные точки, координатные линейки закреплены сверху и слева.
Когда узлы и область processing-связей уходят за viewport с запасом 100 px,
снизу появляется кнопка возврата, которая вписывает граф в видимую область.
Переводы интерфейса и локальных Preview-записей описаны в `docs/LOCALIZATION.md`.

## Workspace projects

Native smoke проверяет F11 → fullscreen, Esc → восстановление, параметр с
клавиатуры → host → child и закрытие после отключения host. На Mutter/Xwayland
окно нужно активировать обычным pointer click: `XSetInputFocus` сам по себе
недостаточен для доставки тестовых XTest-клавиш. С реальной активацией сценарий
прошёл на release bundle; это не замер FPS и не проверка нескольких мониторов.

Workspace — независимый локальный проект с названием, описанием, узлами,
геометрией, связями, параметрами и аннотациями портов. Кнопка названия над канвасом
открывает список проектов, создание нового и менеджер рабочих зон. Старый граф
мигрирует в первый проект без удаления библиотеки и пресетов. Переключение
очищает временный фокус/соединение/выделение и закрывает окна прежних узлов;
импортированные экземпляры получают новые IDs, чтобы окна разных проектов
не переиспользовали чужое состояние.

Менеджер поддерживает открытие, переименование/описание, удаление с подтверждением,
экспорт/импорт `.qualia-workspace` и отправку в Marketplace. Удаление последнего
проекта оставляет новый пустой Workspace; библиотека модулей не удаляется.
Формат обмена `qualia-workspace` версии 1 содержит полный граф и зависимости
`slug`, `version`, `releaseId`, до 500 узлов и 8000 связей, файл до 2 MiB.
Импорт атомарный: недоступные версии показываются списком, частичный проект не
создаётся. Embedded manifests не считаются установленными модулями: host использует
свои Preview-записи, локальную библиотеку и опубликованные точные releases.
Ничего не исполняется при импорте; скачивание/проверка подписанных бинарных пакетов
остаётся отдельной незавершённой runtime-задачей. Перед обменом UI предупреждает
об удалении приватных параметров, токенов и локальных путей из графа.

В Marketplace добавлен раздел Workspaces с существующими карточками, фильтрами и
paging. `workspace_catalog` хранит декларативный пакет; миграция
`supabase/migrations/20261003122742_workspace_catalog.sql` должна быть отдельно
развёрнута на backend. Клиент отправляет собственную запись на модерацию через
GitHub session, но не может выставить `published`, менять утверждённые документы
или подменять автора. Публично видны только одобренные записи. Миграция проверена
на изолированном PostgreSQL 17 fixture `supabase/tests/workspace_catalog_test.sql`;
на удалённый проект автоматически не применялась.

## Workspace presets

Пресет имеет JSON-формат `qualia-workspace-preset` версии `1` и содержит имя и
список до 500 module slugs:

```json
{
  "format": "qualia-workspace-preset",
  "version": 1,
  "name": "Research chain",
  "modules": ["core.gain", "user.example.filter"]
}
```

Пресет сохраняется в локальных preferences и доступен в Explorer. При загрузке
уже доступные модули фильтруют библиотеку Workspace; опубликованные отсутствующие
slugs дополнительно запрашиваются из Marketplace metadata. Если каталог
недоступен или slug не опубликован, пресет всё равно загружается, а missing IDs
показываются в Explorer и уведомлении. Импорт и экспорт выполняются через
desktop file picker.
